# Zapret Hub — диагностика (подпроект 2, с подпроектом 9)

Дата: 2026-10-17. **Делается после подпроекта 8** (стратегии Flowseal на zapret2): circular есть только в zapret2,
а после 8 у кандидатов полный набор и текущую стратегию можно дополнять, а не заменять. Основа: спецификация каркаса (`2026-10-10-zapret-hub-core-design.md`, разделы 4, 13),
маршрутизации (`2026-10-17-zapret-hub-router-design.md`), zapret2.

## 1. Зачем

Пользователь нажимает «Диагностика», когда что-то не работает. Главные случаи (его слова): голос Discord
висит на «Подключение к RTC»; Dead by Daylight не находит матч или скачет пинг. Хаб не просто показывает
отчёт, а **сам находит рабочий путь**: определяет, какой адрес не работает, проверяет его всеми
способами, выбирает лучший, возвращает всё как было, объясняет, что не так, и даёт кнопку «Применить».

Решения пользователя (2026-10-17):
- Сам перебирает варианты, находит рабочий, откатывает к исходному, говорит, что не так, кнопка
  «Применить».
- Во время перебора голос и матч могут отваливаться — допустимо.
- Режим оценки на выбор: «сам» (пробы хаба) или «со мной» («зайди в голосовой чат и скажи, работает ли»).
- Виновника ищем по **живым соединениям программы**, не по списку адресов.
- Для любой программы плюс готовые профили.
- Перед «Применить» перепроверить остальные профили и предупредить о поломках.
- Разным сервисам — разные приёмы: решается через **zapret2 circular**. Подпроект 9 («тест для
  circular») входит сюда.
- Перебираются все пути: напрямую мимо всего, zapret/zapret2 со стратегиями и приёмами, точечно через
  прокси, прокси вместе с zapret и т.д. Выбирается лучший, а не первый рабочий.

## 2. Цели, не-цели, анти-цели

Цели:
- Найти конкретные адреса (IP:порт, протокол, домен), на которых программа не получает ответа или
  получает плохой.
- Для каждого найти лучший путь и объяснить причину простыми словами.
- Применить найденное одной кнопкой, не сломав другие профили.
- Собирать и пополнять управляемую хабом circular-стратегию zapret2 из найденных приёмов.
- То же из CLI (агент проводит диагностику без пользователя в режиме «сам»).

Не-цели:
- Linux, tg-ws-proxy (подпроекты 7, 6).
- Проблемы, не связанные с сетью (аккаунт Discord, античит, падения игры).
- Измерение скорости канала, подбор VPN-серверов в NekoBox.

Анти-цели (провал, даже если «работает»):
- Система осталась в изменённом состоянии после диагностики, отмены или падения хаба.
- «Применить» молча ломает другой профиль.
- Вывод «починено» без измерения, которое это показывает.
- Применение без нажатия кнопки пользователем (в CLI — без явной команды `diag apply`).

## 3. Сценарий

1. Вкладка «Диагностика»: выбрать профиль (Discord, Dead by Daylight, YouTube) или программу (список
   запущенных процессов или выбор exe); режим «сам» / «со мной»; «Начать».
2. **Наблюдение.** Хаб просит воспроизвести проблему («зайди в голосовой канал», «начни поиск матча»)
   и 30 с (настраивается, 10–120 с) только смотрит соединения программы, ничего не меняя, при текущих
   настройках (стратегия, маршрутизация как есть). По ходу показывает найденные адреса.
3. **Виновники.** Адреса со сбоями (раздел 5) — список; пользователь может снять лишние галочки. Нет
   виновников → «соединения программы проходят; если проблема есть, она не в сети» + сводка, что видели.
4. **Перебор путей** (раздел 6) для каждого виновника; прогресс, текущий путь, найденное.
   В режиме «со мной» на каждом пути — вопрос «Работает? Да / Нет / Не знаю».
5. **Откат** к исходному состоянию.
6. **Итог** (раздел 8): что не так, лучший путь, сравнение путей, предупреждения по другим профилям,
   «Применить».
7. «Отмена» на любом шаге → откат, частичный итог из уже проверенного.

## 4. Профили

Профиль — встроенный TOML (в exe), переопределяемый файлом `data\diag\profiles\<id>.toml`:

```toml
id = "discord"
name = "Discord"
apps = ["Discord.exe", "DiscordPTB.exe", "DiscordCanary.exe"]
hint = "Зайдите в голосовой канал"         # что воспроизвести при наблюдении
domains = ["discord.com", "discord.gg", "discord.media", "discordapp.com", "discordapp.net"]
# Пробы для проверки «сам», когда трафик программы не повторяется сам; и для перепроверки профиля.
[[probe]]
kind = "https"         # https | discord-ip-discovery | stun | ping | live
target = "discord.com"
[[probe]]
kind = "discord-ip-discovery"
target = "observed"    # адреса, найденные наблюдением
```

Встроенные: Discord (голос: UDP, IP discovery; текст: HTTPS, gateway), Dead by Daylight
(`DeadByDaylight-Win64-Shipping.exe`, `bhvrdbd.com`, игровой UDP — проба `live`), YouTube (браузеры:
`chrome.exe`, `msedge.exe`, `firefox.exe`, `brave.exe`, `opera.exe`; `googlevideo.com`, `youtube.com`;
HTTPS; QUIC виден только в наблюдении — отдельной пробы QUIC нет). Профиль «Любая программа» строится на лету: exe, без доменов, пробы `https` для TCP с
SNI из наблюдения и `live` для UDP.

## 5. Наблюдение и виновники

Новый крейт `diag`; наблюдение — через `router`:
- Владельцы сокетов и образы процессов — те же `owner`/`Images`, что в маршрутизации 3-го этапа.
- Пакеты — дескриптор WinDivert с `FLAG_SNIFF` (копии, ничего не задерживается и не меняется), фильтр
  по локальным портам сокетов программы (обновляется по событиям SOCKET), бюджет фильтра — как в
  маршрутизаторе. Работает и при включённой маршрутизации (видит исходные адреса до NAT).
- DNS — тот же сниффер `Names` (имя для адреса); при системном DoH (`doh::system_doh`) — пометка, что
  имена могут быть неизвестны, используется SNI из ClientHello (TCP 443) и `Host`.

Счётчики на поток (адрес назначения, порт, протокол): пакеты и байты туда/обратно, для TCP — повторы
SYN, RST в первых 4 КБ ответа, время SYN→SYN-ACK; для UDP — время первого ответа, доля «запрос без
ответа» по окнам 1 с.

Виновник (пороги для данных и UDP — как у детектора неудач zapret2, `standard_failure_detector`, чтобы
оценка хаба и circular совпадали; SYN без ответа circular не видит — он считает только повторы с
данными, — поэтому для таких виновников путь «приём zapret2» не предлагается):
- TCP: ≥3 повтора SYN без ответа; RST или HTTP-редирект провайдера в первых 4 КБ ответа; ≥3 повтора
  данных в первых 32 КБ.
- UDP: ≥4 пакетов туда и ≤1 обратно за окно наблюдения.
- «Плохой» (не мёртвый): медиана RTT выше 250 мс или потери UDP выше 20 % — проверяется тем же
  перебором, лучший путь сравнивается по задержке.
Адреса группируются по домену и /24, чтобы не перебирать 40 голосовых серверов по отдельности: из группы
берутся до 3 представителей.

**Трафик через системный прокси.** Программа может отправлять часть соединений на локальный прокси
(`127.0.0.1:<порт NekoBox>`), а не напрямую. Пакеты такого потока хаб видит только до loopback: адреса
назначения нет, и маршрутизатор его не перехватит (правило по программе ловит только прямые
соединения). Наблюдение помечает такие потоки «через системный прокси» и узнаёт их судьбу из журнала
прокси (ниже). Порт прокси берётся из настроек маршрутизации; системный прокси — из
`HKCU\…\Internet Settings` (`ProxyEnable`, `ProxyServer`), только чтение.

**Источники сверх пакетов** (только чтение; нет файла — источник пропускается, итог помечает это):
- **Журнал NekoBox** (`<папка NekoBox>\config\neko.log`, папка — новая настройка, по умолчанию берётся из
  пути к процессу `nekobox.exe`/`nekobox_core.exe`). Строки
  `inbound/mixed[mixed-in]: inbound connection to <host>:<port>` и следующая с тем же id
  `outbound/direct[bypass]` или `outbound/vless[proxy]` (любой тип исходящего) дают для каждого домена
  программы, куда его отправил прокси: **напрямую** (тогда он идёт через zapret и провайдера) или **через
  VPN**. Время в квадратных скобках (`[id 8.85s]`) — длительность соединения. `ERROR … dns` и время
  исходящего соединения больше 2 с — признак сломанного DNS прокси (картина Р3 в разделе 16).
- **Маршруты NekoBox** (`config\routes_box\<имя>`, JSON: `direct_domain`, `proxy_domain`, `direct_dns`,
  `remote_dns`) — чтобы объяснение называло правило, из-за которого домен ушёл напрямую, и что в нём
  поменять. **Хаб конфиг NekoBox не меняет**: в итоге — инструкция, что поменять руками (раздел 8).
- **Журнал Discord** (`%APPDATA%\discord\logs\renderer_js.log`, также `discordptb`, `discordcanary`) —
  состояние голоса глазами клиента; разбор строк — картины Р2 и Р6 в разделе 16. Читаются только строки с
  отметкой времени не раньше начала наблюдения.
- Журнал DbD зашифрован — не используется.

## 6. Пути

Для каждого виновника — набор путей. Каждый путь — временная конфигурация, ставится через ту же очередь
операций, что тесты стратегий (один снимок на всю диагностику, раздел 9).

| Путь | Как ставится |
|---|---|
| Как сейчас | ничего не менять (точка отсчёта) |
| Напрямую мимо всего | служба zapret остановлена, маршрутизация на паузе |
| Стратегия Flowseal / zapret2 / своя | как в тестере: стратегия запускается процессом winws/winws2 |
| Приём zapret2 | одна стратегия-кандидат circular (раздел 7), запущенная отдельно |
| Прокси точечно | маршрутизация с одним временным правилом: адрес виновника (/32, порт, протокол, программа); zapret как сейчас |
| Прокси без zapret | то же, служба zapret остановлена |
| Расширить правило программы | правило маршрута программы профиля с недостающим протоколом (`udp` → `both`), если виновник — поток этой программы другого протокола (картина Р1) |

Поток «через системный прокси» (раздел 5) хаб перенаправить не может: для него путь не перебирается, а
проба `https` к его домену идёт двумя способами — через прокси (`--socks5-hostname`) и напрямую
(`--noproxy`); итог говорит, каким из них домен работает и куда его сейчас отправляет NekoBox.

Порядок: «как сейчас» → «напрямую» → «прокси точечно» (если прокси отвечает) → стратегии по последнему
рейтингу тестов → приёмы zapret2. Бюджет: 10 мин на диагностику (настраивается); по истечении — итог из
проверенного. Стратегии, чей фильтр не покрывает протокол и порт виновника, пропускаются (разбор
аргументов уже есть в `zapret`/`zapret2`).

## 7. Проверка пути и circular

Оценка пути:
- Режим «сам»:
  - `https`: `curl` к домену с подстановкой адреса виновника (`--resolve`), TLS-рукопожатие и ответ;
  - `discord-ip-discovery`: UDP-пакет IP discovery (74 байта) к голосовому серверу, ждём ответ;
  - `stun`: STUN Binding Request;
  - `ping`: ICMP (только для задержки, не для «работает»);
  - `live`: протокол неизвестен (игровой UDP DbD, любая программа) — хаб снова наблюдает живой трафик
    программы 10–15 с и применяет критерии раздела 5. Хаб просит пользователя продолжать попытки
    (поиск матча) в начале перебора.
  - Каждая проба 3 раза; путь «работает», если ≥2 из 3; задержка — медиана.
- Режим «со мной»: путь ставится, хаб показывает «Проверьте: <подсказка профиля>. Работает?» —
  «Да / Нет / Не знаю»; параллельно идут пробы режима «сам», их результат виден рядом.

Ранжирование: работает > не работает; среди работающих — по медиане задержки, затем по потерям, затем
по «точечности» (прокси точечно и приём zapret2 лучше смены глобальной стратегии при равенстве ±15 %).

**Circular (подпроект 9).** Хаб ведёт управляемую стратегию zapret2 `zapret2:hub-circular`
(`<папка zapret2>\strategies\hub-circular.txt`, как свои стратегии 5-го подпроекта):
- Кандидат — весь набор приёмов одного профиля стратегии zapret2 (его `--lua-desync` с их `--payload`,
  `--out-range`, блобами и `--lua-init`), а не одна строка: приёмы профиля работают вместе. Берутся
  профили встроенных (после подпроекта 8 — и перенесённых Flowseal) и своих стратегий, чей фильтр
  (`--filter-tcp/udp`, `--filter-l7`) покрывает протокол и порт виновника. `--hostlist`/`--ipset`
  кандидата заменяются на виновника: `--ipset-ip` группы (/24) для адреса, `--hostlist-domains` для
  домена — иначе приём не коснётся его трафика.
- Каждый кандидат проверяется как отдельный путь (раздел 6).
- Профиль zapret2 в `hub-circular` на группу (протокол + порты + l7) содержит `circular` и стратегии
  1…N — сработавшие приёмы по рангу; первым идёт лучший. Детектор неудач — стандартный, с порогами
  раздела 5. Неработавшие приёмы в набор не входят.
- Найденное хранится в `data\diag\circular.toml` (группа → упорядоченные приёмы с датой и
  измерениями); новая диагностика пополняет и переупорядочивает; файл стратегии генерируется из него.
- `hub-circular` = **текущая стратегия zapret2 с добавленными circular-группами** (решение исполнителя
  по поручению пользователя: «как лучше»): всё, что работало, продолжает работать; группы виновников
  встают перед профилями текущей стратегии. Слияние — существующим `zapret2::circular::merge`.
  Если текущая стратегия — Flowseal (zapret1), основой берётся её перенос из подпроекта 8.
- UDP в circular: `merge` сейчас отказывает (`NoteKind::NotTcp`), а детектор zapret2 умеет UDP
  (`udp_out`/`udp_in`); поддержка UDP добавляется, диапазоны `--in-range`/`--out-range` для UDP —
  по счёту пакетов, а не по TCP-смещениям (сверить с руководством zapret2).
- Применение `hub-circular` = применение стратегии zapret2 (служба zapret2), после перепроверки
  профилей (раздел 8).

## 8. Итог и «Применить»

Итог на виновника: адрес/домен, что видели («UDP уходит, ответов нет»), таблица путей (работает,
задержка, потери, ответ пользователя), лучший путь и объяснение по шаблону:
- работает только «прокси точечно» → «провайдер блокирует адрес; zapret не помогает; через прокси
  работает»;
- работает «напрямую мимо всего», не работает «как сейчас» → «мешает текущая стратегия/маршрутизация»;
- работает стратегия/приём → «DPI провайдера; помогает приём X»;
- ничего не работает → «адрес недоступен ни одним путём, включая прокси: вероятно, проблема на стороне
  сервиса или прокси» + что проверено;
- сеть в порядке, а клиент застрял (картина Р6 раздела 16) → «сеть не виновата: <что видно в журнале
  клиента>» + что сделать (перезайти, перезапустить клиент собеседника).

«Применить» по виду лучшего пути:
- прокси точечно → правило маршрута (имя `diag-<профиль>`, адреса/подсеть группы, порты, программа
  профиля) + включить маршрутизацию;
- стратегия → применение стратегии (как сейчас);
- приём zapret2 → обновить `hub-circular` и применить её;
- «напрямую» → предложить выключить мешающее (маршрут или правило), с пояснением;
- расширить правило программы → `routes edit` этого правила с новым протоколом;
- домен «через системный прокси» уходит напрямую и не работает, а через VPN работает → кнопки нет:
  инструкция для NekoBox («Настройки → Маршрутизация → Basic: убрать `<домен>` из Direct, добавить в
  Proxy») с именем правила из `routes_box`; после правки — «Проверить снова» (повтор пробы и журнала).

Перед кнопкой: **перепроверка остальных профилей** — их пробы (`https`, `discord-ip-discovery` к
последним виденным адресам, `stun`) при пути-кандидате и при исходном состоянии; профиль, который был
рабочим и стал нерабочим, — предупреждение «сломает: YouTube (googlevideo не отвечает)». Кнопка
остаётся, предупреждение показывается рядом; при поломке хаб предлагает вариант через circular, если он
есть. Перепроверка входит в бюджет и тоже откатывается.

## 9. Состояние и откат

- Один снимок на всю диагностику (`zapret::snapshot`, как в тестере, с `pending.json`): служба, стратегия,
  движок; плюс состояние маршрутизации (`router_enabled`, правила, пауза) — новый раздел снимка в
  `pending.json`, чтобы откат после падения хаба вернул и её.
- Откат: в конце, при отмене, при ошибке; при падении хаба — при следующем запуске, как для тестов.
- Пока идёт диагностика: тесты стратегий и применение стратегий заблокированы (ошибка, как во время
  прогона), маршрутизация — на паузе вне путей «как сейчас» и «прокси».
- Отчёты: `data\diag\<дата-время>.json` (наблюдение, виновники, пути, итог); последние 20.

## 10. Интерфейс

- Новая вкладка «Диагностика». Быстрые проверки с вкладки «Zapret» переезжают сюда (раздел «Быстрая
  проверка» сверху); на «Zapret» остаётся строка состояния со ссылкой.
- Шаги на одной странице: выбор → наблюдение (живой список адресов) → виновники (галочки) → перебор
  (прогресс, таблица путей) → итог (объяснение, «Применить», предупреждения, «Подробнее»).
- Режим «со мной» — карточка-вопрос поверх прогресса, с уведомлением Windows, если окно скрыто.
- Трей: «Диагностика…» открывает вкладку; во время диагностики значок показывает «идёт диагностика».
- Тексты — русские, как во всём интерфейсе.

## 11. CLI

Протокол 4. Команды:

| `diag profiles` | профили |

Ход — в stderr, как у `tests run --wait`. Агент по умолчанию — режим «сам». Профиль только с пробой

## 12. Крейты и границы

- `diag` (новый): профили, наблюдение (через `router`), виновники, пути, оценка, ранжирование, итог,
  `circular.toml` и генерация `hub-circular`. Зависит от `exec`, `probe`, `zapret`, `zapret2`, `tester`
  (запуск стратегии на время), `router`.
- `router`: публичный режим наблюдения (sniff по программе, счётчики потоков) и временное правило без
  записи в `routes.toml`.
- `probe`: пробы `discord-ip-discovery`, `stun`, `https --resolve`.
- `src-tauri`: команды, очередь, вкладка, трей; CLI — команды `diag`.

## 13. Тестирование

- Чистая логика без прав: критерии виновника на синтетических счётчиках, группировка, ранжирование,
  шаблоны объяснений, разбор фильтров стратегий → кандидаты, генерация `hub-circular` из
  `circular.toml`, откат снимка (как тесты тестера).
- Пробы: локальные UDP/TCP-эхо-серверы на loopback (IP discovery, STUN).
- Живые (`#[ignore]`, с правами): наблюдение за `curl.exe`, путь «прокси точечно».
- Разбор журналов на образцах из раздела 16: фрагменты `neko.log` (direct/proxy по id, медленный DNS) и
  `renderer_js.log` (DAVE застрял один / с собеседником, DAVE завершён, VOICE_STATE_UPDATE) →
  ожидаемая картина; каждая картина Р1–Р6 — свой тест на синтетических счётчиках и журналах.
- Ручной чек-лист в `docs/cli.md`: голос Discord с плохой стратегией → диагностика находит голосовой
  сервер и путь; DbD в поиске матча; «со мной»; отмена посреди перебора → всё как было; падение хаба
  посреди перебора → откат при запуске; предупреждение по другому профилю; `hub-circular` применяется
  и голос работает.

## 14. Риски

- **Живой трафик нужен для `live`.** Если программа перестала повторять попытки, путь не оценить —
  хаб пишет «нет попыток программы» вместо «не работает».
- **Голосовые серверы Discord меняются** между звонками: наблюдение даёт текущие; при новом звонке
  адрес может быть другим — поэтому правила прокси ставятся на группу (/24) и домен, а circular — по
  порту и l7, не по адресу.
- **Время.** Десятки стратегий × виновники × 3 пробы: бюджет и порядок (раздел 6) ограничивают; в итоге
  видно, что не успели.
- **circular хранит выбор в памяти winws2** (на хост, сбрасывается при перезапуске службы): первым
  ставим лучший приём, чтобы и после перезапуска сразу работало.
- **Приоритет WinDivert:** sniff-дескриптор не мешает zapret и маршрутизатору (копии пакетов), но
  добавляет нагрузку; наблюдение ограничено портами программы.

- **IPv6** вне объёма (как в маршрутизации): потоки IPv6 видны в наблюдении с пометкой «IPv6 не
  поддерживается», пути для них не проверяются.

## 15. Оставлено исполнителю

Точные тексты интерфейса, раскладка вкладки, формат JSON отчёта, лимиты фильтра sniff, таймауты проб,
порядок стратегий при равном рейтинге, имена типов.

## 16. Картины сбоев из живого разбора (2026-10-18)

Разбор шёл вручную, агентом, у пользователя: zapret2 `ALT11`, NekoBox (VLESS Reality, системный прокси
`127.0.0.1:18082`, Direct-список с `discord.*`), маршрутизация хаба. Каждая картина — признаки, как хаб
их находит, объяснение и что предлагается. Диагностика проверяет все картины, а не первую подходящую:
в разборе их было несколько одновременно.

**Р1. Правило программы не покрывает протокол (DbD «нет соединения с онлайн сервисами»).**
- Признаки: правило `DBD Process` с `protocol = "udp"`; игра часть запросов шлёт через системный прокси
  (там `*.live.bhvrdbd.com` отвечает `200` за 0,85 с), а часть — напрямую по TCP; напрямую
  `https://steam.live.bhvrdbd.com/api/v1/healthcheck` висит 10 с и падает по таймауту (curl `e28`).
- Как найти: виновник — TCP-поток программы с правилом, которое этот протокол не ловит; проба `https`
  к домену напрямую и через прокси.
- Объяснение: «провайдер не пускает к серверам Behaviour напрямую; правило DbD ведёт через прокси только
  UDP».
- Предложение: путь «Расширить правило программы» (`udp` → `both`). Проверено: помогло.

**Р2. Голосовой UDP Discord до Cloudflare.**
- Признаки: голос идёт на `104.29.x.x:19294–19344` (Cloudflare), демонстрация экрана — на
  `35.217.x.x:50000+` (GCP) и работает. Голос по правилу «Discord голос» через прокси подключается:
  `RTC connected to media server`, а `Connected with local address <адрес>` показывает адрес VPN-сервера
  (`<адрес VPN-сервера>`), то есть медиасервер видит VPN.
- Как найти: UDP-виновник по разделу 5; адрес из `Connected with local address` сравнивается с внешним
  адресом прокси (проба через прокси) — так видно, каким путём реально ушёл голос.
- Предложение: правило «Discord голос» (готовый набор), путь «прокси точечно».

**Р3. Прокси «не работает»: сломан прямой DNS NekoBox.**
- Признаки: проверка прокси в хабе то проходит, то нет; в `neko.log` исходящие соединения по 5–10 с; прямой
  DNS NekoBox (`doh.pub`, `120.53.53.53`) не отвечает или отвечает медленно.
- Как найти: время `outbound/...` в журнале больше 2 с у большинства соединений; проба через прокси к
  домену из Direct-списка медленная, к домену через VPN — нормальная.
- Объяснение: «NekoBox долго ищет адреса через свой прямой DNS; каждое соединение ждёт».
- Предложение (без кнопки): сменить `direct_dns` в NekoBox на рабочий
  (`https://common.dot.dns.yandex.net/dns-query` помог: соединения стали ~165 мс).

**Р4. Подмена DNS провайдером и системный DoH.**
- Признаки: обычный DNS (UDP 53 к `8.8.8.8`, `1.1.1.1`) для `youtube.com`/`googlevideo.com` отвечает
  NXDOMAIN, DoH Cloudflare отвечает адресами. При включённом системном DoH Windows сниффер `Names` слеп, и
  доменные правила маршрутизации не срабатывают (`doh::system_doh`).
- Как найти: проба — один и тот же домен через UDP 53 и через DoH; расхождение → подмена.
- Объяснение и предложение: «провайдер подменяет DNS» → включить в Windows DoH «только зашифрованный»,
  шаблон автоматический; при этом предупредить, что доменные правила ослепнут (правила по IP — нет).

**Р5. Режим белых списков у провайдера.**
- Признаки: российские сайты (`ya.ru`) открываются, VPN-сервер не отвечает вообще (даже TCP SYN), затем
  может отказать и DNS.
- Как найти: проба `https` к `ya.ru` проходит, к нескольким зарубежным адресам (VPN-сервер, `1.1.1.1`,
  `discord.com`) — SYN без ответа по всем путям, включая прокси.
- Объяснение: «провайдер пускает только в разрешённые сети; ни zapret, ни прокси это не обходят» — итог
  без перебора путей. В разборе прошло после переподключения к Wi-Fi.

**Р6. Голос подключён, но шифрование DAVE не завершается (звука нет).**
- Признаки в `renderer_js.log`: `RTC connected to media server`, `DAVE protocol init`,
  `Received MLS external sender package`, `Sending MLS key package` — и дальше 15 с и больше нет
  `Received MLS commit`/`welcome`, `DAVE protocol state update` остаётся с пустым `epochAuthenticator`,
  а `Heartbeat ACK received` идёт и `last received sequence number` не растёт. Иногда рядом
  `No VOICE_STATE_UPDATE received within 30000ms`.
- Служебный канал голоса (`wss://*.discord.media:2096`) идёт через системный прокси; по `neko.log` видно,
  ушёл ли он напрямую (через zapret) или через VPN. В разборе он сначала шёл напрямую по Direct-правилу
  `discord.media`; после переноса в Proxy картина не изменилась.
- Как отличить, чья сторона: другие участники — строки `Creating user: <id> with audio SSRC: <n>`
  с SSRC не нашим (свой — из `Creating connection to … with audio ssrc: <n>`).
  - Один в канале и застрял → клиент сам должен создать группу (`Sending MLS commit + welcome message`);
    не создал → наша сторона: проверить служебный канал напрямую и через VPN.
  - Есть собеседники, служебный канал жив по любому пути, ключ отправлен, ответа нет → ключи должен
    разослать клиент уже сидящего участника: **сторона собеседника**. В разборе так и было: помог
    перезапуск Discord у собеседника.
- Объяснение: «сеть в порядке: соединение с голосовым сервером есть, но собеседник не прислал ключи
  шифрования» + «пусть собеседник перезайдёт или перезапустит Discord; проверить себя — зайти в канал
  одному».
- Режим «сам» картину Р6 видит только по журналу; путь не перебирается (сеть не виновата), кроме
  проверки служебного канала через VPN, если он шёл напрямую.

Не сетевое, но видно в разборе: Defender помещает `zapret-hub.exe` в карантин (ложные `Bearfoos.A!ml`,
`Persistence.A!ml`) — вне объёма диагностики (раздел 2); совет пользователю — исключение папки хаба в Defender.
