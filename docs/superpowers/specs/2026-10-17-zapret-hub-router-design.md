## 1. Цель

Отправлять выбранный трафик через локальный SOCKS5-прокси (NekoBox и подобные) без TUN: по IP и
подсетям, по доменам и по программам, для TCP и UDP. Остальной трафик идёт как обычно — через
zapret или напрямую. Голос Discord работает через прокси без отдельного окна PowerShell.

## 2. Объём и этапы

Одна спецификация, три плана и три слияния:

1. **UDP по IP и подсетям.** Правила, `routes.toml`, вкладка «Маршруты», статистика, трей, CLI,
   защита от петли (дескриптор сокетов, раздел 4.4), профиль «Discord голос». Прямая замена скрипта.
2. **TCP и домены.** Перенаправление TCP в локальный приёмник, SOCKS5 CONNECT, таблица DNS
   «IP → домен», профиль «Discord целиком».
3. **Правила по программе.** `apps` в правилах, колонка «Программа» в потоках, профиль
   «Dead by Daylight».

Каждый этап — рабочее приложение. Поле правила из следующего этапа — ошибка проверки с именем поля
(«`apps` пока не поддерживается»), а не молчаливый пропуск.

**Вне объёма:** IPv6, авторизация в прокси, несколько прокси, правила «не через прокси», перехват
по SNI (раздел 13, решение 4), DNS по TCP/DoH/DoT.

## 3. Архитектура

- **`crates/router`** — вся логика; от Tauri не зависит (core). Модули:
  - `rules` — формат `routes.toml`, проверка, профили, совпадение правил;
  - `packet` — разбор и сборка IPv4/UDP/TCP, контрольные суммы через WinDivert-helper;
  - `divert` — загрузка `WinDivert.dll` (`LoadLibraryW` + `GetProcAddress`), дескрипторы, фильтры;
  - `socks` — клиент SOCKS5: рукопожатие, CONNECT, UDP ASSOCIATE;
  - `udp` — UDP-потоки (этап 1);
  - `tcp` — перенаправление и приёмник (этап 2);
  - `dns` — разбор ответов и таблица «IP → домен» (этап 2);
  - `owner` — PID и exe по событиям сокетов, процесс прокси (этапы 1 и 3);
  - `stats` — счётчики по правилам и потокам, снимок для UI и CLI.
  - Поправка при реализации этапа 1: `udp` и `stats` слиты в `flows.rs` (потоки, счётчики, снимок для UI и CLI);
    PID по событиям сокетов — в `owner.rs`.
- **`src-tauri`**: команды, вкладка, пункт трея, восстановление `router_enabled` при запуске,
  пауза на время тестов. Тело команды — вызов `router`.
- **Где работает.** Внутри процесса хаба (уже с правами администратора). Отдельной службы нет:
  закрыли или уронили хаб — Windows закрывает дескрипторы WinDivert, трафик идёт как обычно.
- **Состояние.** Флаг `router_enabled` в `zapret-hub.toml`; при запуске хаба маршрутизация
  восстанавливается. Правила — `data/routes.toml`.

### 3.1. WinDivert

- DLL: `<zapret>\bin\WinDivert.dll` (Flowseal) или
  `<zapret2>\binaries\windows-x86_64\WinDivert.dll`. Берётся DLL папки запущенного сейчас движка:
  драйвер у движков общий, DLL должна совпадать с загруженным драйвером. Если движок не запущен —
  DLL Flowseal, если её нет — zapret2.
- Не найдена ни одна DLL или `WinDivertOpen` не открылся — маршрутизация недоступна с причиной
  (текст ошибки Windows); остальной хаб работает.
- Приоритет наших дескрипторов — 1000, выше `winws`/`winws2`: трафик из правил до zapret не
  доходит. Подтвердить на этапе 1 живым тестом, что `winws` открывает свои дескрипторы с меньшим
  приоритетом (по исходникам — 0).

## 4. Путь пакета

### 4.1. Дескрипторы

1. **Перехват (NETWORK, приоритет 1000).** Фильтр:
   `outbound and !loopback and ip and (<udp-часть> or <tcp-часть>)`, где части собираются из
   таблицы маршрутов: подсети из правил + IP из таблицы DNS (этап 2), с портами правил. Пустая
   таблица — фильтр `false`: дескриптор остаётся открытым только для отправки пакетов (решение этапа 1). Таблица изменилась — новый фильтр, новый дескриптор, затем
   закрытие старого; не чаще раза в секунду. На этапе 2 сюда же входят ответы локального
   приёмника (раздел 4.3).
2. **DNS (NETWORK, SNIFF, этап 2).** `inbound and udp.SrcPort == 53`; только чтение.
   Поправка при реализации этапа 2: фильтр `ip and udp and udp.SrcPort == 53` без `inbound` (ответы локального
   резолвера идут по loopback и не «входящие»); таблица DNS живёт в `Router` и переживает паузы.
   Правило с доменами добавляет в TCP-часть фильтра SYN к своим портам (SYN ждут в очереди, пока фильтр
   не пересоберётся с адресом из ответа DNS; не вышло — SYN уходит без изменений); для правила без
   диапазонов остальных частей нет. Диапазонов не больше 64: сверх этого ближайшие сливаются.
3. **Сокеты (SOCKET, SNIFF).** События `CONNECT` и `BIND` с PID. Этап 1 — только защита от петли;
   этап 3 — правила по программе.

### 4.2. UDP (этап 1)

Улучшенный перенос скрипта:
- Поток — ключ «локальный порт → адрес:порт назначения». Новый поток: TCP к прокси, рукопожатие без
  авторизации, `UDP ASSOCIATE` с адресом назначения в запросе (VLESS без XUDP привязывает UDP-сессию
  к одному адресату — как в скрипте), локальный UDP-сокет на loopback.
- Исходящий пакет — заголовок SOCKS5 UDP + данные → реле. Ответ реле — пакет IPv4/UDP от сервера к
  локальному адресу и порту, инжектится как входящий с адресом исходного пакета (биты Outbound и
  Impostor сброшены), контрольные суммы через `WinDivertHelperCalcChecksums`.
- В заголовке SOCKS5 UDP — домен (тип 3), если IP есть в таблице DNS (этап 2), иначе IP.
- Поток без пакетов 30 с закрывается.
- **Прокси не принял поток** (нет ответа за 3 с, отказ, обрыв): поток помечается «напрямую» с
  причиной, его пакеты уходят без изменений (`WinDivertSend` исходного пакета). Пока поток
  открывается, его пакеты ждут в очереди (до 64 пакетов, дальше старые выбрасываются).

### 4.3. TCP (этап 2)

- Перенаправление приёмом «отражения»: исходящий SYN к адресу из таблицы меняет местами адреса,
  порт назначения становится портом локального приёмника, пакет отправляется как входящий.
  Ответы приёмника (исходящие с его порта) переписываются обратно и отправляются как входящие.
  Таблица NAT по локальному порту клиента хранит исходный адрес назначения; запись живёт, пока
  живо соединение (FIN/RST в обе стороны или 2 мин без пакетов).
  Поправка при реализации этапа 2: после FIN в обе стороны или RST запись живёт ещё 10 с (последний ACK),
  после 2 мин простоя тоже: реле закрывается, и FIN приёмника ещё доходит до клиента;
  приёмник один на сеанс маршрутизации. Полузакрытое соединение: EOF закрывает одну половину, реле живёт
  до `IDLE` (120 с без пакетов); ошибка, остановка или пропавшая запись NAT закрывают обе.
- Приёмник (один на хаб, `0.0.0.0:<свободный порт>`) по порту клиента берёт исходный адрес, делает
  `CONNECT` к прокси (с доменом, если известен) и гоняет байты в обе стороны.
- Прокси не ответил за 3 с или отказал: соединение закрывается (RST), а адрес на 60 с помечается
  «напрямую» — следующие SYN к нему не перехватываются. Первое соединение не восстановить:
  программа переподключится.
  Поправка при реализации этапа 2: SYN, не дошедший до приёмника за 2 с (короче трёх секунд повтора SYN в Windows), тоже отправляет адрес «напрямую» на
  60 с (брандмауэр Windows); возврат прокси после недоступности снимает пометки; адреса живых записей NAT
  остаются в фильтре, даже если правило выключено или запись DNS истекла. Пауза и выключение рвут
  перенаправленные соединения: записи NAT и перехват живут ещё 100 мс, чтобы FIN приёмника дошёл
  до клиента.

### 4.4. Защита от петли

Через дескриптор сокетов хаб знает PID каждого потока. Не перехватываются:
- трафик своего процесса;
- трафик процесса, слушающего порт прокси (`GetExtendedTcpTable` по порту из `socks5`;
  обновляется при каждой проверке прокси).

Если PID потока ещё неизвестен (событие сокета опоздало), первый пакет ждёт его до 50 мс, затем
решение принимается без PID.

Поправка при реализации этапа 3: PID берётся сначала из событий сокетов, затем из
`GetExtendedTcpTable`/`GetExtendedUdpTable` (сначала IPv4, при промахе таблицы IPv6 — сокеты с двойным
стеком; PID 0 пропускается), и только потом первый пакет ждёт до 50 мс. «Владелец неизвестен»
запоминается по локальному порту до события сокета или его закрытия: захват не ждёт 50 мс на каждый поток
процесса, чей сокет был открыт до сеанса.

### 4.5. DNS (этап 2)

- Разбор ответов A и CNAME. Имя совпало с доменом из правила (сам домен или поддомен) — все IP из
  ответа, включая конец цепочки CNAME, записываются за исходным именем.
- Срок записи — TTL, но не меньше 5 минут: программы кэшируют адреса дольше TTL.
  Поправка финального ревью этапа 2: TTL не больше суток (TTL с верхним битом — ноль, RFC 2181), чтобы
  подделанный ответ не закрепил адрес навсегда; адрес живого потока UDP или записи NAT не истекает, пока
  поток жив (и ещё 5 минут после).
- DNS по TCP, DoH, DoT не видны. В редакторе правила с доменами — подсказка: выключить «безопасный
  DNS» в браузере или добавить подсети.

### 4.6. Правила по программе (этап 3)

PID → путь exe (`QueryFullProcessImageNameW`, кэш по PID с проверкой времени старта). Поток
совпадает с `apps`, если совпало имя файла (без учёта регистра) или полный путь. TCP решается на
SYN (PID известен из события `CONNECT`, ждём до 50 мс, как в 4.4); UDP — на первом пакете потока.
Для правил по программе фильтр перехвата включает весь трафик с портами и протоколом правила, а
решение «прокси или мимо» принимается в хабе: не совпавшие пакеты сразу отправляются обратно без
изменений.

Поправка при реализации этапа 3 (решение о стоимости перехвата):
- **TCP** — только первые SYN (`tcp and tcp.Syn and !tcp.Ack`) на портах правила, как у правил по
  доменам. Решение на SYN; адрес назначения совпавшего соединения входит в часть «удерживаемых» адресов
  (механизм этапа 2), а SYN ждёт фильтра с этим адресом. Остальные сегменты чужих соединений через хаб не
  идут.
- **UDP** — весь исходящий UDP на портах правила (без портов — весь), но только пока запущена программа
  из UDP-правила (есть живой процесс с совпавшим exe в кэше путей). Пока она не запущена, UDP не
  перехватывается совсем. Процесс узнаётся по событию сокета или по первому потоку; программа, запущенная
  до включения маршрутизации, — по `GetExtendedUdpTable`: при открытии и раз в 2 с, пока UDP-правило по
  программе простаивает. Живость процесса из кэша — `GetExitCodeProcess`, кэш путей хранится по PID и
  времени старта (переиспользованный PID не совпадает) и переживает паузы.
- Не совпавшее решается сразу и запоминается на поток («напрямую: нет правила»), дальше пакеты идут без
  изменений одним поиском в таблице потоков.
- Редактор советует указать порты: так через хаб идёт меньше UDP.

## 5. Правила

### 5.1. Формат `data/routes.toml`

```toml
[[rule]]
name = "Discord голос"
enabled = true
protocol = "udp"                 # "tcp" | "udp" | "both"
ports = ["19294-19344", "50000-65535"]   # пусто или нет поля = все порты
ips = ["104.29.0.0/16", "35.217.0.0/16"]
domains = ["discord.media"]      # этап 2: домен и все поддомены
apps = []                        # этап 3: "Discord.exe" или полный путь (оканчивается на .exe)
```

- Имя: правила имён стратегий (zapret2 5.2: 1–40 символов, латиница, цифры, пробел, `-_.`) плюс
  кириллица; уникально без учёта регистра.
- Должна быть хотя бы одна цель (`ips`, `domains` или `apps`).
- Поток идёт в прокси, если совпало хотя бы одно включённое правило: протокол и порт совпали, и
  совпала любая из целей. Порядок правил не важен.
- Поправка при реализации этапа 3: элемент `apps` — имя файла (без `\`, `/` и `:*?"<>|`) или
  абсолютный путь (`C:\…`, `C:/…`, `\\server\share\…`), в обоих случаях оканчивается на `.exe` без учёта
  регистра. Сравнение без учёта регистра, `/` читается как `\`: элемент с `\` — весь путь exe, иначе —
  имя файла exe.
- Проверка: подсети IPv4 (`a.b.c.d` или `a.b.c.d/n`), порты 1–65535 и диапазоны `a-b` с `a ≤ b`,
  домены по LDH без схемы и пути. Ошибка — с номером строки файла и полем.
- Файл перечитывается при изменении (проверка времени записи раз в 2 с). Битый файл — правила
  остаются прежними, на вкладке ошибка с местом.

### 5.2. Профили

Кнопка «Добавить из профиля»; после добавления правило правится как обычное.
- **Discord голос** (этап 1): UDP, порты `19294-19344, 50000-65535`, подсети `104.29.0.0/16`,
  `35.217.0.0/16`; с этапа 2 ещё домен `discord.media`.
- **Discord целиком** (этап 2): `discord.com`, `discord.gg`, `discordapp.com`, `discordapp.net`,
  `discord.media`, оба протокола.
- **Dead by Daylight** (этап 3): `DeadByDaylight-Win64-Shipping.exe` и домен `bhvrdbd.com`.
  Поправка при реализации этапа 3: оба протокола (`both`), без портов.

«Импорт из файла» добавляет в правило строки `.txt`: IP и подсети — в `ips`, остальные — в
`domains`; пустые и `#` пропускаются, дубликаты отбрасываются.

## 6. Прокси

- Адрес — `socks5` из настроек. Нет адреса — маршрутизация не включается («укажите SOCKS5 в
  настройках»).
- Проверка раз в 10 с (рукопожатие). Работавший прокси считается недоступным после двух неудачных
  проверок подряд: одна потеря рукопожатия не обрывает идущий звонок. Недоступен — новые потоки идут
  напрямую, в шапке и на значке трея «прокси недоступен, трафик идёт напрямую». Вернулся — новые
  потоки снова через прокси, а потоки, ушедшие напрямую из-за отказа прокси (недоступен, авторизация,
  нет UDP), закрываются и со следующим пакетом открываются заново через прокси.
- Просит авторизацию — ошибка «прокси просит авторизацию», потоки напрямую.
- Отклоняет `UDP ASSOCIATE` — «прокси не поддерживает UDP» с подсказкой про mixed inbound в NekoBox;
  UDP-потоки напрямую.

## 7. Взаимодействие с остальным хабом

- **Тесты стратегий.** На время прогона маршрутизация на паузе (дескрипторы закрыты), после —
  восстанавливается. В шапке «пауза: идёт тест».
- **Смена движка или папки** — маршрутизация перезапускается с DLL нового движка (3.1).
- **Изменение правил** действует на новые TCP-соединения и на следующие UDP-пакеты; открытые
  TCP-соединения остаются как были.

## 8. Окно

Вкладка **«Маршруты»**:
- **Шапка:** переключатель «Маршрутизация», состояние прокси (отвечает + задержка / недоступен /
  ошибка), пауза, итог «через прокси / напрямую» (байты и потоки).
- **Правила:** переключатель, имя, сводка («UDP · 2 подсети · 1 домен»), трафик по правилу.
  Редактор с проверкой полей на лету, «Добавить из профиля», «Импорт из файла», удаление с
  подтверждением.
- **Потоки** (раз в секунду): протокол, назначение (IP:порт и домен), программа (этап 3), правило,
  «прокси» или «напрямую» с причиной, вверх/вниз, длительность. Фильтр «только по правилам / все».
  Закрытые потоки видны ещё 30 с.
  Поправка при реализации этапа 3: «все» — потоки с правилом и потоки без правила, пойманные ради
  правил по программе (строка с правилом «—» и причиной «напрямую: нет правила»). Строк без правила в
  списке не больше 500 (самые старые отбрасываются), в итоги «через прокси / напрямую» они не входят.

**Трей:** пункт «Маршрутизация: вкл/выкл»; пометка на значке, когда прокси недоступен.

## 9. CLI

По образцу cli, JSON-вывод и коды выхода оттуда же:

| Команда | Действие |
|---|---|
| `router on` / `router off` | включить/выключить, пишет `router_enabled` |
| `router status` | состояние, прокси, пауза, итоги |
| `routes list` | правила со сводкой и статистикой |
| `routes show <имя>` | правило целиком |
| `routes add <имя> --file rule.toml` / `routes edit <имя> --file rule.toml` | добавить/заменить; файл — одна таблица `[rule]` без `name` |
| `routes enable\|disable\|remove <имя>` | |
| `routes preset <профиль>` | добавить правило из профиля (`discord-voice`, `discord`, `dbd`) |
| `routes flows [--all]` | текущие потоки |

Изменения через pipe разрешены (это не выбор папки, cli/core).

## 10. Тестирование

- **Модульные (без системы):** пакеты IPv4/UDP/TCP (разбор, сборка), отражение адресов и NAT,
  сборка фильтра WinDivert, совпадение правил, проверка и разбор `routes.toml`, профили, импорт,
  разбор DNS-ответов (A, CNAME, сжатие имён, битые пакеты), таблица DNS со сроками.
- **SOCKS5-клиент** против тестового SOCKS5-сервера на loopback внутри теста: CONNECT, UDP
  ASSOCIATE, отказ, просьба авторизации, таймаут, обрыв.
- **Живые с WinDivert** — `#[ignore]`, только с правами администратора.
- **Ручной чек-лист:** голос Discord через NekoBox при выключенном скрипте; выключить NekoBox —
  голос идёт напрямую, на вкладке предупреждение; правило по домену после этапа 2; DbD по exe
  после этапа 3; тест стратегий ставит маршрутизацию на паузу.

## 11. Риски

- **Приоритет `winws`.** Если zapret откроет дескриптор с приоритетом выше нашего, трафик из
  правил пройдёт через desync. Проверяется живым тестом на этапе 1.
- **DoH.** Домены из правил не находятся, если программа резолвит сама. Смягчение — подсказка и
  подсети. Шифрование DNS в самой Windows (`DohFlags` != 0 у адаптера или профиля Wi-Fi, политика
  `DoHPolicy` = 3, `EnableAutoDoh` = 2) хаб читает из реестра: `RoutesView.system_doh`, и при правилах с
  доменами вкладка «Маршруты» предупреждает; флаги отключённых адаптеров тоже считаются.
- **Задержка первого пакета** до 50 мс, пока ждём PID (4.4).
- **Антивирусы** — как в core: перехват трафика выглядит подозрительно; драйвер уже стоит у
  пользователя вместе с zapret.
- **Драйвер держит хаб.** Пока маршрутизация работает, её дескрипторы держат WinDivert загруженным
  и без `winws`: проверка «WinDivert без winws» скрыта, а удаление WinDivert и служб идёт на паузе
  маршрутизации.
- **Смена фильтра.** Пока новый дескриптор открыт, а старый ещё не закрыт, два дескриптора одного
  приоритета могут дважды обработать повторно отправленный пакет. Страдают только счётчики.
- **DLL занята.** Однажды запущенная маршрутизация держит `WinDivert.dll` движка загруженной (файл
  занят), пока хаб не закрыт: распаковать обновление Flowseal или zapret2 поверх папки можно только
  при закрытом хабе (так же в README).
- **DLL выбирается при синхронизации** (запуск хаба, сохранение настроек, конец паузы): смену движка
  в обход хаба роутер не видит до следующей синхронизации. Пункт ручного чек-листа в `docs/cli.md`.
- **Больше 64 диапазонов во всех правилах** (поправка этапа 2): ближайшие диапазоны сливаются, фильтр
  шире правил, совпадение сверяет хаб, лишнее уходит без изменений. Предел: слитый диапазон правила
  без портов (объединение «Discord целиком» без портов и широкого диапазона) может захватить весь
  трафик к широкому диапазону: нагрузка на процессор и задержка в долгой работе.
  Не влезло и после слияний или WinDivert отказал (поправка финального ревью этапа 2): причина
  «too many rules for the capture filter», тот же текст фильтра не открывается снова, пока он не изменится.
- **Брандмауэр Windows и отражённый SYN** (этап 2). Приёмник слушает `0.0.0.0`; Windows может спросить
  про брандмауэр для `zapret-hub.exe` или молча блокировать входящее. Хаб правил брандмауэра не
  добавляет. Заблокировано — через 2 с адрес на 60 с идёт напрямую, причина видна во вкладке; цена:
  пользователю один раз разрешить хабу доступ.
- **SYN раньше ответа DNS** (этап 2). SYN, отправленный до разбора подсмотренного ответа DNS с этим
  адресом, идёт напрямую: держать неизвестные SYN значило бы задерживать каждый SYN на машине
  (профиль «Discord целиком» без портов). Цена: изредка первое соединение напрямую.
- **Поток UDP во время смены фильтра** (этап 2). Поток UDP, начавшийся, пока открывается новый
  дескриптор, может перейти с прямого пути на прокси посреди потока (QUIC при этом откатится на TCP).
- **Адрес → последнее имя** (этап 2). Адрес помнит последнее имя, под которым его видел DNS; CONNECT и
  ATYP 3 в заголовке UDP несут это имя, даже если программа спрашивала другое имя того же адреса.
- **Пауза рвёт TCP** (этап 2): перенаправленные соединения обрываются на паузе и при выключении;
  программа переподключается.
- **Весь UDP через хаб, пока запущена программа** (этап 3). Пока запущена программа из UDP-правила, через
  хаб идёт весь исходящий UDP машины на портах правила (чужие пакеты уходят дальше без изменений); без
  портов — весь UDP. Цена: нагрузка на процессор; смягчение — подсказка в редакторе указать порты.
  Проверяется чек-листом (пункт 33 `docs/cli.md`); выше 10 % процессора — записать сюда.
- **Браузер в `apps` переоткрывает фильтр на каждый адрес** (этап 3). Каждый новый адрес назначения
  совпавшего TCP-соединения входит в фильтр, поэтому фильтр пересобирается. Апгрейд: часть
  `tcp.SrcPort` по портам совпавших сокетов.
- **Первые пакеты UDP программы до пересборки фильтра** (этап 3). Если первый сокет программы — UDP и он
  открыт раньше, чем фильтр пересобрался, первые пакеты потока уходят напрямую (как «поток UDP во время
  смены фильтра»).
- **Первый SYN программного правила без портов** (этап 3). Такое правило (пресет DbD, оба протокола) ловит первый SYN каждого соединения машины, запущена программа или нет: поиск владельца (перебор таблицы, если событие запаздывает; до `PID_WAIT` 50 мс при промахе), время старта процесса и строка «нет правила» — всё на единственном потоке захвата. Проверяется чек-листом (пункт 33 `docs/cli.md`).
- **Не unicast.** Multicast (224.0.0.0/4), broadcast (255.255.255.255) и пакеты с адреса 0.0.0.0
  (DHCP) в прокси не идут никогда, даже если совпали с правилом.
- **Прокси только локальный** (раздел 1): сокеты реле привязаны к loopback, поэтому адрес прокси не
  на loopback маршрутизация отклоняет с причиной.

## 12. Поправки к core

- core 13 говорил «правила маршрутизации через SOCKS5 и их статистика» — без изменений; добавлен

## 13. Решения

Формат «что — почему — цена ошибки».

1. **Внутри процесса хаба, без службы.** Хаб и так запускается автозапуском с правами
   администратора; служба — второй процесс и протокол без явной пользы. Цена ошибки: без хаба
   маршрутизации нет; крейт без Tauri, служба добавляется позже.
2. **Прокси недоступен — напрямую.** Цель — обход блокировок, а не анонимность. Цена ошибки: при
   падении прокси трафик из правил на время идёт мимо него; режим «только через прокси» для
   правила добавляется позже.
3. **Один прокси из настроек.** Других сценариев у пользователя нет. Цена ошибки: поле `proxy` в
   правиле добавляется без ломки формата.
4. **Домены через подсмотр DNS, без перехвата по SNI.** Решение на SYN, одинаково для TCP и UDP,
   не ломает правила по программе, не пропускает весь веб через хаб. Цена ошибки: DoH-клиенты не
   ловятся по домену; перехват по SNI для отдельных правил добавляется поверх.
5. **Только IPv4.** Скрипт и списки — IPv4. Цена ошибки: при IPv6-маршруте до сервиса трафик
   идёт мимо прокси.
6. **Дескриптор сокетов уже на этапе 1.** Без PID не защититься от петли через трафик прокси.
   Цена ошибки: до 50 мс на первый пакет потока.
7. **Пауза на время тестов.** Иначе тест мерил бы прокси, а не zapret. Цена ошибки: на время
   теста трафик из правил идёт напрямую.
